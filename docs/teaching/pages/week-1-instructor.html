› Answer key

Why the word is "harness" and not "framework" or "scaffolding"

› Answer key

Decided 2026-08-28. Harness carries the right two implications and the alternatives do not: it is the thing you build around something you do not control, and it is the thing that bears the load.

  • Scaffolding implies you take it down when the real thing is finished.

Whole room · 8 min

This is the correction that has to come before anything else, because the drawing is almost always wrong in the same way. Ask for the number first: how many times did that run call the model? Most of the room says two.

How the loop ends

The room says two, and the third call is the whole point

› Answer key

Three model calls, two tool executions. The third call is the one that produces resolve, and it is invisible in the trace because it runs no tool.

Inside one step

Context is state, and state has a lifetime

› Answer key

The full argument is docs/teaching/notes/context-as-state.md. The compressed version for this beat:

  • What the agent knows is assembled fresh each step from things that stay true for very different lengths of time.
  • A system prompt written months ago, a policy fetched a second ago, and an account note written by somebody who does not work here all arrive in the same shape, with the same authority, and with no timestamp.
  • Most "the model got confused" incidents are a state-management bug under a different name.

Rebuilding from scratch is the right instinct and it does not help here: _build_prompt already does it, and rebuilding from stale history reproduces the stale fact perfectly.

› The wrong answer worth spending time on

"Carry the thought forward, then." A good instinct and it is quiz Q14 in miniature. It costs tokens on every step, it can lock the model on to an early wrong line, and in make injected it would restate an attacker's instruction as the agent's own words, where a rule about untrusted tool output no longer reaches it.

Do not settle it. The teaching point is that it is a real trade-off with two defensible answers and the repository made neither: it just happened. Ask who would have signed off on the choice.

Probe. If you carried it forward, what would you have to write next to it? A timestamp. That is week 3.

Odds, or what is possible

The session spine, and the test question it becomes

› Answer key

Odds: the model, the temperature, the system prompt, what enters the context. All in llm.py, all inside the probabilistic component.

Possible: MAX_STEPS and the TOOLS dictionary. Both enforced outside it.

This returns as quiz Q11, where "a more capable model with better instruction-following" is offered as a durability boundary and is not one. Ask Q11 late, after the bake-off has made a better model look like the answer.

› The wrong answer worth spending time on

"Temperature zero makes it deterministic, so that one changes what is possible." The best wrong answer in the topic, and it comes from somebody who has read the API documentation carefully.

Q1 · What "keeping context current" actually costs

recall · renders on the learner check · the opener, and it kills the wrong instinct before it forms

An agent reads an account balance at step 1 and issues a credit at step 6. Which change removes the largest class of failure?

  • A. Rebuild the prompt from scratch on every turn
  • B. Re-read the balance inside issue_credit, at execution time — correct
  • C. Increase the context window so nothing is evicted
  • D. Add "always verify the balance is current" to the system prompt

A is the trap and it is the commonest answer here. The repository already does it and the bug survives. C holds more stale facts and makes the oldest one older. D is a prompt instruction against a probabilistic component, guarding an irreversible action.

Follow-up for D: how would you find out, on the Tuesday it did not comply? Nobody has an answer, and that is the beat.

Q9 · Which boundary saves the most money

apply · renders on the learner check · the anchor question of the durability set

One boundary, added before that night. Which one prevents the most loss?

  • A. A 5-second timeout on the payments call
  • B. An idempotency key on the refund — correct
  • C. A named outcome and non-zero exit on step-budget exhaustion
  • D. A nightly spend cap of ₹300,000

Run the case cold. Give the room "The system" and "The night" from notes/case-one-slow-night.md, about 300 words, and nothing else. The comparison table is the answer key and must not be on screen.

Q3 · Reading our own code

apply · prose, taken in the room · put src/llm.py on screen

This line does one thing right and one thing wrong. Name both. — for h in state["history"]: lines.append(f" {h[‘action’]}({h[‘args’]}) -> {h[‘result’]}")

Ask this immediately after Q1, because their own repository is the proof of Q1's answer and reading it themselves is worth more than being told.

Q5 · Idempotency is state

apply · prose, taken in the room · ties to make retry and teardown question 1

make retry pays ₹3,600 on one ₹1,200 double-charge across three runs in which the agent reasons correctly every time. Which two pieces of state are missing, and where would each live?

This is the question that makes the room say the word "idempotency" out loud, which is the precondition for Q13 and Q14. Ask it before either of them, never after.

Q13 · Where does the idempotency key come from

apply · renders on the learner check · ask immediately after the room says "we need idempotency"

The agent generates an idempotency key and passes it to the payments provider. The queue redelivers the request and a fresh run starts. Which key prevents the second payment?

  • A. A uuid4() minted at the start of the run
  • B. A hash of the conversation history so far
  • C. The refund request id carried on the queue message — correct
  • D. A hash of (account_id, amount)

D is the one worth the minute. It is the answer from somebody who has thought about it properly and landed one step short, and the failure it causes is invisible: a customer owed two refunds gets one, and nothing anywhere reports it.

Follow-up: whose job is it to put the id on the message? Not the agent's. That is the handover between the queue and the tool, and it is exactly teardown question 1.

Q11 · Which of these is not a durability boundary

recall · renders on the learner check · ask late, after the bake-off

Three of these are durability boundaries and one is not. Which is not?

  • A. A ceiling on the amount a single tool call can move
  • B. Human confirmation before an irreversible action
  • C. A more capable model with better instruction-following — correct

Ask this late and never early. It is worth far more after ninety minutes in which a better model has looked like the answer, and after 03:02 showed it helping on one ticket and hurting on another.

Q14 · Who dedupes

judge · prose, taken in the room · the best distractor in the bank, because the wrong answer sounds like good engineering

A room proposes: put every previous action into the context, and have the model check whether it already paid before paying again. Give three reasons this does not hold, and the version of the idea that does.

Protect the time for this one. It is what a senior room proposes, it sounds like good engineering, and taking it apart is the session's spine in miniature: a boundary changes the set of possible actions, an instruction changes the odds.

Credit the instinct — it is half right and the half it gets right matters. Once the tool refuses, swallowing that refusal is the worst option available. A silent refusal is a step-budget stop by another name, which is drill 1.

Q4 · The cache framing
