What guardrails are, and the topics today covers

Guardrails are runtime checks placed around an AI model or agent, so the system stays secure, predictable, compliant and fast enough. "Runtime" means they run on every request, not once at design time. The field groups them by where they run:

  • Input guardrails run before the model is called. Example: mask a PAN number in the customer's message before the model sees it.
  • Output guardrails run after the model answers, before a person reads it or a tool acts on it. Example: refuse a credit of ₹5,000 to an account that does not exist.
  • Operational and system guardrails run around the whole system. Example: stop calling a payment service that has failed five times in a minute.

What this topic is for

Where does a limit have to sit to stop a caller nobody has written yet?

By the end of it you can tell a policy from a wish, place a limit at the point that covers every caller, and name the callers it still misses.

Two terms in the title. A guardrail is a control on what the agent is allowed to do, and at 00:37 you make that definition exact. Policy enforcement means checking a written rule at the moment an action is attempted.

What a limit is, and why the agent needs one

A limit is a rule with a number in it: the most an action may do without anybody else agreeing. For the dispute agent the first limit is no single credit above ₹1,200, which is one month of the ₹1,200 Pro plan.

An agent needs limits more than ordinary software does, because the model chooses the arguments. In week 1 nobody typed "pay ₹5,000 to account 9999". The model picked those values while it ran. A limit is the part that still says no when the model picks badly.

Week 1 ended with one question about your own system: where is the limit written down, and who agreed to it? Most people came back with an honest answer. The limit is a number inside a function, and nobody agreed to it. Somebody typed it during a sprint, and it has been policy ever since.

Writing the number in a file is the easy half, and most of this room already does it. The half that costs money is which callers your control covers. The ₹5,000 at 01:12 is what that half costs.

What this topic is not. It is not the gate that asks a person, which is topic 2. It is not a test that proves the limit works, which is week 3. It is not a defence against the poisoned ticket from week 1, which is week 4. And it is not a model deciding for you, which is topic 4 at 03:18.

One small example of each plane

Short Python, so the idea is concrete. These are sketches, not production code.

# Input guardrail: mask a PAN before the model sees the message
import re
PAN = re.compile(r"\b[A-Z]{5}[0-9]{4}[A-Z]\b")
def mask_input(text):
    return PAN.sub("[PAN]", text)

# Output guardrail: refuse a tool call whose arguments break the rules
from pydantic import BaseModel, PositiveInt
class Credit(BaseModel):
    account_id: str
    amount: PositiveInt            # a negative or text amount fails here
def check_credit(args, accounts, ceiling=1200):
    c = Credit(**args)             # raises on a malformed call
    if c.account_id not in accounts:
        return "refuse: account does not exist"
    if c.amount > ceiling:
        return "refuse: over the ceiling"
    return "allow"

# Operational guardrail: stop calling a service that keeps failing
FAILS, LIMIT = [], 5
def call_payments(fn, *args):
    if len(FAILS) >= LIMIT:
        raise RuntimeError("circuit open: payments failed 5 times, not calling")
    try:
        return fn(*args)
    except Exception:
        FAILS.append(1)
        raise

When a check runs: synchronous, asynchronous, layered

A check can run at three moments relative to the work. Topic 4 at 03:18 goes deeper, with timings.

  • Synchronous, also called in-band or blocking. The work waits until the check says yes. Example: the credit is not paid until the ceiling check passes. Nothing unchecked gets through, and every request waits a little longer.
  • Asynchronous, also called out-of-band. The work goes ahead and the check runs beside it. Example: a chat reply streams to the customer while a slower check reads it, and the stream is cut if the check fails. Nobody waits, but you need a way to take the result back.
  • Layered. Several checks in a row, cheapest first. Example: a fast rule catches most bad requests in well under a millisecond, and only the unclear ones go to a slower model. You get wide coverage without making every request slow.

The rule of thumb: if the action cannot be undone, like a payment, its checks must be synchronous.

So what is a guardrail

A guardrail is anything that stands between what your agent decides to do and what actually happens.

Read that sentence for what it excludes. A line in the system prompt is not a guardrail, because the model can decide not to follow it and nothing stands between that decision and the ledger. A dashboard is not a guardrail either, because it stands after the money moved. A retry policy is not one. A code review is not one.

The test is whether it is on the path. If the action can reach the world without passing through your control, your control is advice. At 01:12 today that distinction costs ₹5,000, and the thing that tells you is a counter that does not move.

What did the check have to know

"The check" means the policy check you just watched refuse ticket #9999 at 00:23: a few lines of Python that run before a tool is called and decide allow or refuse. Before it can decide, it needs some facts. Four facts, and no more than four. Say them out loud before you read them.

#The factWhere it comes fromCost
1Which action is thisThe dispatch already has it. It is the tool name.Free
2Can it be undoneThe grade you gave each tool in week 1Free
3What is the limitA file. This topic is about which file.Free
4What has already happenedMemory that outlives the programExpensive

The first three are written down somewhere and cost nothing to read. The fourth needs a store you can restart. That is topic 3, at 02:34.

Notice what is not on that list. The check does not need to know what the model thought, how confident it was, or which model it was. None of those four facts come from the model at all.

Why the second fact is there

Whether an action can be undone looks like a detail. It is the fact that decides everything else.

  • It decides whether to check at all. lookup_account can run a thousand times and the world is unchanged. A ceiling in front of it costs latency and protects nothing.
  • It decides whether you are allowed to fix things afterwards. If an action can be undone, there is an afterwards: notice it at 9am, reverse it, apologise. A dashboard and an alert are a real answer. If it cannot be undone there is no afterwards, and the only place a control can exist is before the call.
  • It is what makes the rule writable. "Ask a human before an irreversible action" is a rule you cannot write until something in the code knows which actions are irreversible.

What this topic is for

What does your code do when nobody approves inside the time you set?

By the end of it you can stop an action you cannot undo, record why it was stopped, and say what your code does when nobody approves inside the time you set.

The field shortens this to HITL, for human in the loop: the system stops and waits for a person to approve before it acts. You will meet the acronym in every vendor's documentation and in every audit conversation you ever have about an agent. The guardrail itself is the human gate.

The hard part is not the asking. The hard part is everything on the other side of the ask. Who is allowed to answer, how long you wait, what happens at 2am, and what the whole arrangement costs when it runs 110 times a day.

# src/approve.py
import json, sys, time
from .tools import TOOLS
QUEUE = "data/approvals.jsonl"
TIMEOUT_S = 18 * 60          # today's experiment; your system picks its own number

def decide(approval_id, by, approve):
    rows = [json.loads(line) for line in open(QUEUE)]
    row = next(r for r in rows if r["id"] == approval_id)
    if row["status"] != "pending":
        return f"already {row['status']}"            # one approval, one payment
    if by == "agent":
        return "refused: the requester cannot approve its own request"
    if time.time() - row["asked_at"] > TIMEOUT_S:
        row.update(status="refused", decided_by="timeout")   # your default
    elif approve:
        TOOLS[row["action"]](**row["args"])
        row.update(status="approved", decided_by=f"human:{by}")
    else:
        row.update(status="refused", decided_by=f"human:{by}")
    with open(QUEUE, "w") as f:
        f.writelines(json.dumps(r) + "\n" for r in rows)
    return row["status"]

if __name__ == "__main__":
    approval_id, by, answer = sys.argv[1], sys.argv[2], sys.argv[3]

What this topic is for

Idempotency means running a request twice does the same thing as running it once. Written as maths: f(f(x)) = f(x).

The concept

The fix that holds

The fix is not a better data structure. It is a different place.

The ledger here is a Python list, so there is no store to put a rule in. Make one. A sqlite file is in the standard library, it needs no service, and it survives the process that wrote it.

Why a read then a write loses

That distinction is the whole segment, and it is worth being slow about.

A read to check, followed by a write, has a window between the two. Two processes both read "not paid", both decide to pay, and both write. Nothing in your code is wrong when you read it line by line. The two lines are simply not one thing.

An insert against a unique key has no window, because the database serialises the two for you. You are not writing a better check. You are moving the check to something that cannot be raced.

Best practices firms follow

  • The caller chooses the key from the business identity (the dispute), and sends it on every retry.
  • The store that holds the money enforces it with a unique constraint, not a read followed by a write.
  • Record pending and done separately, so a crash between the two is visible and can be finished or undone.
  • Keep keys at least as long as a retry can arrive, including manual re-runs days later.
  • Bound every retry: a fixed number of attempts with growing waits, then stop and alert.
  • Test from two processes, not just by calling the function twice in one test.

Idempotency in guardrailed systems: the wider picture

Reading, not a segment. The lab covers the first two ideas. The rest are where the same rule shows up elsewhere in an AI system.

  • Why retries are riskier around a model. A guardrail that rejects malformed output often asks the model again: the "repair loop". Each repair is a new model call that may produce a different tool call. If the first attempt already paid, the repair can pay again.
  • Key injection. Create the key before the tool runs and pass it in. Some systems hash the session, the step number and the arguments together. That stops a retry inside one session from paying twice. It does not stop a redelivered ticket, which starts a new session, so for money the key should be the dispute itself.
  • Two-phase actions: prepare, then commit. First check and record the intent as pending (prepare). Only then perform the effect and mark it done (commit). A crash between the two leaves a visible pending row rather than silence.
  • One approval, one payment. The approval step from topic 2 must treat a second "yes" on the same request as a no-op.
  • Masking personal data twice must not change it. If a masking step runs twice, [PERSON_1] must not become [ENTITY_2]. Keep a per-session table so the same name always maps to the same placeholder.
  • Caching guardrail verdicts. Hashing the exact system prompt and user input (for example with SHA-256) lets you reuse a verdict and save time and money. A "similar enough" semantic cache is riskier: two requests that look alike can deserve different answers.
  • Rebuilding context cleanly. When the agent corrects itself, replace the bad turn instead of stacking error messages in the history, so running the correction twice gives the same context.
  • Circuit breakers on repair loops. Cap how many times a failed check may ask the model again, then stop and hand over to a person.

Layered defence: the tiered gateway pattern

The idea first. Put several checks in a row, from cheapest to most expensive, like security at an airport. A fast rule handles the clear cases, and most requests stop there. Only what the rule cannot decide goes on to a small classifier. Only what the classifier cannot decide goes on to a model that judges. What tier 3 looks like in code

A sketch of a specialised guardrail model, Llama Guard, used as a checker. It reads a conversation and answers "safe", or "unsafe" with a category code. It runs on a GPU you host.

from transformers import AutoTokenizer, AutoModelForCausalLM
name = "meta-llama/Llama-Guard-3-8B"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name)

def tier3(ticket_text):
    chat = [{"role": "user", "content": ticket_text}]
    ids = tok.apply_chat_template(chat, return_tensors="pt")
    out = model.generate(ids, max_new_tokens=10)
    verdict = tok.decode(out[0][ids.shape[-1]:], skip_special_tokens=True)
    return verdict.strip()          # "safe", or "unsafe" and a code such as "S2"

def check(credit, ticket_text):
    if credit["amount"] > 1200:    # tier 1: a rule, well under 1 ms
        return "refuse"
    if tier3(ticket_text) != "safe":  # tier 3: hundreds of ms
        return "send to a person"
    return "allow"

Notice the order. The ceiling runs first and cannot be argued with. The model only gets a say on what the rule already allowed, so it can make the guard stricter, never looser.

In-band or out-of-band: the latency tax

In-band, or synchronous blocking: every request passes through the checks, often in a proxy or a sidecar, before anything happens. No unchecked output reaches a person or a tool. Every request pays a latency tax, commonly quoted as 50 to 300 ms depending on the checks.

Out-of-band, or asynchronous: the reply streams to the person while the checks run beside it. Nobody waits. When a check fails mid-stream, you need a fast way to take the reply back: close the stream, or run a compensating action that undoes what was done.

So the choice follows the undo question from 00:48. A payment cannot be taken back, so its checks are in-band, whatever the tax. A chat reply can be stopped mid-stream, so a slow judge on it can run out-of-band.

Latency budgeting

Give each endpoint a written budget for guardrail time. For example: no more than 150 ms of checks on an interactive reply. A tier 3 judge alone does not fit inside that, so it goes out-of-band or onto a sample. The budget turns "is this check worth it?" into arithmetic somebody can review.

Engineering trade-offs and operations

Running guardrails in production is a set of trade-offs. Four of them, with where today covers each:

  • Latency budgeting. Every check adds time. Write a budget per endpoint, such as 150 ms of checks on a chat reply, and keep slow model judges out of the fast path. Covered above.
  • False-positive rates. A check that refuses too much drives people around it. Track precision and recall on refusals, and run a changed check in shadow mode before it blocks anyone. Topic 2, 02:24.
  • Observability and audit trails. Count every allow and refusal per rule, and record why each refusal happened and which rule fired, without copying personal data into the log. Topic 1's counters and topic 2's decision log, 01:51.
  • Operating the rules. Version the policy file, give every number an owner, alert when a refusal rate changes sharply, and keep a runbook for the engineer on call. The teardown at 04:15 asks who owns each number.

  • A. Tell the judge, in its prompt, to ignore instructions found in ticket text
  • B. Keep the judge and put a deterministic ceiling underneath it
  • C. Use two judges and require both to agree
  • D. Raise the judge’s confidence threshold
Show the answer

B. A model may widen what gets through a hard limit, and it may never be the limit.

C is the subtle one. Two judges reading the same attacker-written field are not independent, so they agree. Two of something correlated is one control.
