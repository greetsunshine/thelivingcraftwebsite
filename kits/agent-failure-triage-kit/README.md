# The Agent Failure Triage Kit

What your agent should do after a checker says no.

An agent that uses one word, "error", for three different situations will retry the wrong thing, and the expensive version of that mistake is retrying an action that may already have run. This kit separates the three: evidence that is genuinely absent, a dependency that could not be reached, and an action whose outcome nobody established. It gives you the four triage questions in the order to ask them, a runnable simulation of a refund agent that gets it wrong and then right, and twelve failure-injection tests you can copy into your own repository.

The written kit is at [learning.thelivingcraft.ai/resources/agent-failure-triage-kit](https://learning.thelivingcraft.ai/resources/agent-failure-triage-kit). This repository is the code behind it.

## Quick start

Python 3.11 or later. No network, no model calls, no API key. The whole suite runs in under a second.

```
make setup     # a virtualenv in .venv with pytest, jsonschema and PyYAML
make naive     # the story: three refunds, and an orchestrator that believes it made none
make fixed     # the same faults against the corrected design: one refund
make test      # 52 tests, including the twelve failure injections
make matrix    # runs the twelve against BOTH designs, writes tests/naive_vs_corrected.json
make schemas   # regenerates schemas/examples/ from real runs
```

                        Executed / NotExecuted / OutcomeUnknown.
                        No tool ever reports a failure as an empty value.

  fakes.py              Document store, payment provider with a ledger and an

  naive_orchestrator.py Reproduces the story. It has no bug.
  orchestrator.py       The corrected design.
  budgets.py            One TaskBudget per task, shared by every layer.
  policy.py             Reads policies/retry_budgets.yaml.
  clock.py              Virtual time, so nothing sleeps.
  records.py            The rejection record.

schemas/
  rejection_record.schema.json   JSON Schema, draft 2020-12, with the
                                 conditional rules (an uncertain action must
                                 prohibit re-issue; a planned retry must say
                                 what changes; an escalation must name a queue).
  examples/                      Three records, one per class, from real runs.

policies/
  retry_budgets.yaml    What may be retried automatically, by tool type, and
                        the per-task budget. Every number is labelled as a
                        starting point to tune, and a test checks the labels.

tests/
  test_failure_injection.py   T01 to T12. Each states what it injects, what a
                              correct design does, and the smell a failure

  build_examples.py     Writes the three example records.

## The three classes

| Class | Meaning | Correct response |
|---|---|---|
| `missing_evidence` | Something required to decide is genuinely absent. The read completed. | Ask for it. Do not regenerate the answer. |
| `temporary_failure` | A dependency could not be reached, and no side effect occurred. | Bounded retry of the tool, not the model. |
| `uncertain_action` | An action with side effects may or may not have executed. | Do not retry. Reconcile state first, then decide. |

Two more classes exist for completeness: `policy_conflict` (the plan and confirmed state disagree, and state wins) and `unrecoverable` (no justified path remains). `escalate` and `stop` are next steps, not classes.

## The four questions, in order

1. Could an action with side effects already have executed? → `uncertain_action`
2. Is required evidence genuinely absent? → `missing_evidence`
3. Is a dependency temporarily unavailable? → `temporary_failure`
4. Can a named owner resolve it? → `escalate`, otherwise `stop`

Side effects come first because misclassifying an uncertain action as a temporary failure invites a bounded retry, and retrying something that already ran is how one refund becomes three. The mistake in the other direction costs a person looking at a case that did not need one.

| T07 | Document store down beyond the retry budget. | fail | pass |

The naive failures are worth reading as assertions. T08: `9 calls against a budget of 4`. T06a: `assert 30.0 in [2.0]`, it slept on its own guessed backoff and ignored the Retry-After the provider sent. T09: two refunds in the ledger where the checker approved one.

## Adapting this to your own agent

The simulation is deliberately small so the parts you would replace are obvious.

**Your tools go in `fakes.py`'s place.** The only contract they have to honour is the one in `tool_contracts.py`: a read returns `Found`, `NotFound` or `Unavailable`; an action returns `Executed`, `NotExecuted` or `OutcomeUnknown`. If your real client cannot tell "not found" from "could not look", that is the first finding, and it is the root cause in the story.

**Your triage is `triage.py`, and you probably do not need to change it.** The four questions are not specific to refunds. What you may add is how your system answers question 1: which of your calls have side effects, and how you query their state afterwards.

**Your policy is `policies/retry_budgets.yaml`.** Tune every number to your own latency and cost. The test in `tests/test_policy.py` will refuse a number you forgot to label.

**Your tests start from `tests/test_failure_injection.py`.** The ones to port first are T01, T04 and T08. A read that times out while the data is present. A write that times out after it commits. A retry configured at two layers. Three injections, whatever your harness is.

The forty-five minute version of that exercise is on the last page of the kit.

## The story

An illustrative case, not a real incident.

A customer uploads a receipt and asks for a refund. The receipt lookup times out and returns an empty result. The system records "no receipt". The agent recommends a refund; the checker rejects it for missing evidence. The orchestrator retries the model three times, each attempt more confident, and escalates. The lookup itself is never retried. On Monday a human finds the receipt was there all along and approves. The payment call times out. The same retry policy fires three times. Every call reached the provider. The customer is refunded three times.

No component had a bug. The model never hallucinated. `make naive` reproduces it.
